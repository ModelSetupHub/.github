# ModelSetupHub

**مدل‌های AI محلی را نصب، تنظیم و اندازه‌گیری کنید — با هر سطح مهارتی که دارید.**

اجرای مدل‌های AI روی کامپیوتر شخصی امروز ممکن است، ولی راه‌اندازی‌اش دردناک است. کاربر باید بداند کارت گرافیکش چقدر
VRAM دارد، کدام مدل در آن جا می‌شود، چه پارامترهایی را برای سرعت بهتر عوض کند، و وقتی چیزی کار نکرد خطای مبهم
`llama-server` چه معنایی دارد. بیشتر این‌ها حدس‌هایی است پخش‌شده در پست‌های انجمن.

ModelSetupHub یک جعبه‌ابزار متن‌باز است که همین فرایند را کنترل‌شده و قابل اندازه‌گیری می‌کند: سخت‌افزار را می‌شناسد،
سرویس Ollama را مدیریت می‌کند، مدل‌ها را نصب و اجرا می‌کند، و — بخشی که بیشتر ابزارها از آن می‌گذرند — همان پرامپت‌ها را
با چند مجموعه پارامتر مختلف اجرا می‌کند تا ببینید کدام کانفیگ روی دستگاه شما واقعاً سریع‌تر است.

همه‌ی کار واقعی در **Core** انجام می‌شود. سه ریپوی دیگر راه‌های متفاوت رسیدن به آن هستند، برای آدم‌های متفاوت، و روی یک
دستگاه قابل جایگزینی با یکدیگرند.

| ریپو | چیست | برای چه کسی |
| --- | --- | --- |
| [**Core**](https://github.com/ModelSetupHub/Core) | کتابخانه‌ی پایتونی که کار را انجام می‌دهد | اسکریپت‌نویسی خودتان |
| [**MCP**](https://github.com/ModelSetupHub/MCP) | سرور MCP که همان ابزارها را به یک AI agent می‌دهد | توصیف هدف به زبان معمولی |
| [**gui**](https://github.com/ModelSetupHub/gui) | داشبورد وب محلی روی همان توابع | کنترل کامل دستی |

### Core — کتابخانه

پکیج پایتونی که بقیه فقط پوسته‌ی آن هستند. پنج ماژول:

- **`core.System`** — شناسایی سخت‌افزار: جزئیات CPU، ماژول‌های رم، معماری و VRAM کارت‌های گرافیک (NVIDIA، AMD، Intel)،
  دیسک‌ها، و یک اسکنر قابلیت‌ها.
- **`core.ollama`** — چرخه‌ی عمر دیمن Ollama، مدیریت مدل‌های محلی (ساخت، اجرا، بارگذاری، توقف، حذف)، و بنچمارک
  پارامترها با معیارهای توان عبور توکن.
- **`core.python`** — چرخه‌ی عمر محیط مجازی، مدیریت پکیج‌ها با pip، اجرای اسکریپت، و کشف نسخه‌های نصب‌شده‌ی پایتون در
  ویندوز.
- **`core.download_manager`** — دانلود‌منیجر ترتیبی چندفایلی با pause/resume، تلاش مجدد، سرعت و ETA، و لغو.
- **`core.logging`** — لاگ JSON ساختاریافته با برچسب‌گذاری در سطح کامپوننت و ردگیری اکشن‌ها.

```python
from core.ollama import experiment

result = experiment.run_test(
    model="llama3",
    prompts=["Hello, world!", "Summarize the solar system."],
    config={"temperature": 0.7, "num_ctx": 4096},

)
print("Avg output tokens/sec:", result["summary"]["average_output_tokens_per_second"])
```

### MCP — رابط عامل

یک سرور MCP (Model Context Protocol) که جعبه‌ابزار را در اختیار یک AI agent می‌گذارد، تا بتوانید بگویید *یک مدل کدنویسی
مناسب سیستم من نصب کن* و agent خودش مراحل را انتخاب کند. ۵۴ ابزار ارائه می‌دهد — ۴۸ پاس‌ترو نازک به core در حوزه‌های
سیستم، سرویس، مدل‌ها، بنچمارک، محیط‌های پایتون، دانلود و لاگ، به‌همراه ۶ ابزار برای پنل پیشرفت درون گفتگو.

پنل پیشرفت تنها بخش منطق اختصاصی است: یک منبع UI از نوع MCP Apps که عملیات‌های طولانی را در حین اجرا گزارش می‌کند، با
دکمه‌ی Cancel (که عملیات را تمام می‌کند *و* آنچه ساخته را برمی‌گرداند) و Stop برای دانلودها (که انتقال را معلق می‌کند و
با یک درخواست HTTP range ادامه می‌دهد). بعضی ابزارها عمداً ارائه نشده‌اند — مثلاً `write_log`، تا کلاینت نتواند رکورد
جعلی در تاریخ اجرا تزریق کند.

### gui — داشبورد وب

یک رابط محلی روی Flask برای کسی که می‌داند چه می‌خواهد. هیچ تصمیمی جای شما گرفته نمی‌شود؛ این کار را سریع‌تر و دقیق‌تر
می‌کند، اما فرض می‌گیرد می‌دانید context window چیست. چهار تب:

- **System** — اسکن کامل سخت‌افزار؛ از اینجا شروع کنید، چون عدد VRAM تعیین می‌کند چه مدلی قابل بارگذاری است.
- **Ollama** — وضعیت نصب و کنترل پروسه‌ی سرور.
- **Models** — فهرست مدل‌های نصب‌شده و بارگذاری‌شده با اطلاعات، بارگذاری، توقف و حذف روی هر سطر، به‌علاوه فرم‌هایی برای
  اجرای پرامپت، ثبت یک فایل GGUF محلی، و ساختن نسخه‌ی کانفیگ‌شده از یک مدل.
- **Benchmark** — قابلیت شاخص. یک مدل و چند پرامپت انتخاب می‌کنید، چند مجموعه پارامتر دستی از میان ۲۳ گزینه‌ی Ollama یا
  با ورود فایل JSON تعریف می‌کنید، و همه را اجرا می‌کنید. نتیجه با حکم شروع می‌شود: کدام کانفیگ سریع‌تر تولید کرد و با
  چه اختلافی از نفر دوم.

### Website — سایت معرفی

یک سایت استاتیک (HTML و CSS، بدون مرحله‌ی build) که پروژه را به انگلیسی و فارسی معرفی می‌کند.

## از کدام شروع کنم؟

- رابط گرافیکی می‌خواهید و می‌دانید چه می‌کنید ← **gui**.
- ترجیح می‌دهید هدف را توصیف کنید و agent کار را ببرد ← **MCP**.
- خودتان automation می‌نویسید ← **Core** به‌تنهایی.

`Core` یک git submodule در هر دو ریپوی `MCP` و `gui` است، پس هر رابطی باید قبل از اجرا آن را بگیرد.

<div dir="ltr">

```bash
# داشبورد
git clone --recurse-submodules https://github.com/ModelSetupHub/gui.git
cd gui
python -m venv .venv && .venv\Scripts\activate
pip install -e ./core
pip install -r requirements.txt
python app.py            # then open http://127.0.0.1:5000/
```

```bash
# سرور MCP
git clone --recurse-submodules https://github.com/ModelSetupHub/MCP.git
cd MCP
pip install -r requirements.txt
python main.py           # register it in your client under mcpServers
```

</div>

مرحله‌ی `pip install -e ./core` همان چیزی است که راحت از قلم می‌افتد. بدون آن هر درخواست با
`ModuleNotFoundError: No module named 'core'` شکست می‌خورد، چون برنامه submodule را با نام پکیج import می‌کند نه با مسیر.

- پایتون ۳.۱۰ یا جدیدتر
- نصب بودن [Ollama](https://ollama.com/)، برای هر چیزی جز اسکن سخت‌افزار
- Git، برای گرفتن submodule هسته

## چیزهایی که بهتر است پیش از نصب بدانید

اینجا شفافیت از براقی مفیدتر است، پس این‌ها صریح گفته می‌شوند نه پنهان:

- **فعلاً فقط ویندوز.** اسکنر سخت‌افزار روی PowerShell و WMI ساخته شده، پس آن بخش هنوز جای دیگری کار نمی‌کند.
- **داشبورد احراز هویت ندارد.** یک سرور محلی است که endpointهایش Ollama را روشن می‌کنند، مدل بار می‌کنند و حذف می‌کنند، و
  نصب‌کننده روی میزبان اجرا می‌کنند. روی localhost نگهش دارید؛ برای نشستن روی یک اینترفیس شبکه یا پشت reverse proxy عمومی
  ساخته نشده.
- **Ollama لازم است** برای هر چیزی جز تب System.
- **حذف مدل بازگشت‌پذیر نیست**، در هیچ‌کدام از دو رابط.
